The user asked for pros and cons of the two salt options. The comparison turned out to be
mostly about what each site can *reach*, which the roadmap had not said.

Two findings from looking instead of reasoning:

**The sentinel does not need new plumbing for the per-token option.** It loads
`get_token(&tx.token_id, …)` for validation at `processing.rs:87-90`; the salt is fetched at
`:175-179` in the same function. Same transaction, same token — so the value is free and,
more importantly, canonical: one token per transaction means no tie-break rule to invent and
no way for honest nodes to disagree about *which* chain the salt names.

**The committer already chose the per-token option and got it wrong in a different way.**
`epoching.rs:85-90` maps over its in-process `DashMap<Vec<u8>, Token>` and takes `.next()` —
whichever token iteration yields first — and feeds that into the seed for epoch **leader**
election. One token in the cache: fine. Two or more: nothing pins the choice, and a
divergent pick is a divergent leader. The codebase has an explicit house rule against
exactly this (`C6` sort-before-select in `src/epoch/leader.rs`), so this is a known failure
mode implemented at a site that missed it. Worth fixing independently of the salt decision,
because it is a liveness hazard at `shard_count: 1` with a single token per environment —
which is the configuration that actually ships, until someone adds a second token.

Framing that mattered for the answer: both options re-key, so the difference is
**re-key frequency**, not secrecy. A per-token salt changes per block per token; an
epoch-scoped salt is fixed for the whole epoch and readable by anything that can read the
data service, so committees are computable for the entire epoch in advance. Both are
computable by an attacker for a transaction whose id they already chose — the property H3
was buying is late binding, and epoch-scoping mostly gives that away.

Against per-token, honestly recorded: a tip is a moving value, so if the salt is not
*recorded* it is unrecoverable later and the selected committee can never be re-derived —
which is the same hole the quorum-denominator finding describes from the other side. Hence
the paired recommendation: per-token tip **and** record the salt, so verification replaces
recomputation and a mismatch becomes a rejection instead of a fork. The committer's chain
state is deliberately unpersisted (`epoching.rs:81-84`), which is why the epoch-scoped
option costs new persisted state plus a new sentinel read path rather than an argument.

No code changed this turn; the roadmap's Phase 0 item 1 now carries the analysis and a
sharper exit test.
