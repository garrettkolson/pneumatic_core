The question was "how do we implement shards/clusters with dense interiors + gateways".
Before proposing a plan I checked what already exists, because the phrase hides two
different mechanisms — and both turned out to be closer and stranger than "build it".

**Sharding is already there.** `deterministic_select_shard` (`src/epoch/leader.rs:168`)
selects the executor set for a transaction from `(shard_count, tx_id, epoch,
prev_block_hash)`, domain-separated and prev-hash bound so every node recomputes the
same answer without anyone distributing assignments — the property a sharded design
actually needs. And the sentinel *routes on it*: with `env_data.shard_count > 1` it
sends the preload only to that shard's executors.

Then the deflating part: `shard_count` is `1` in `deploy/config/env/env.json:18`, in the
node-server e2e and helper configs, in `pipeline_integration.rs:130`, in
`transport_integration.rs`. Only sentinel unit tests set 2, and the testnet generator
never emits the key. So the shard axis exists in consensus and one routing hop and has
**never been carried across a real cluster**. Given this repo's record — inert
`transport_enabled`, `register_peer` as a test-only directory builder, the `RegisterAck`
placement defect, directory responses never exercised until the peering initiator sent
one — unexercised code is where defects live.

**Gateways are not a config flag.** `rns-core` has a `pub mod transport` with a
`TransportEngine` carrying path tables, announce tables, reverse tables, tunnels,
blackholes, ingress control and a rate limiter — and nothing outside `src/transport/`
constructs or drives it. `rns-net`'s `Transport` is a serial/TCP pipe to an RNode
device. So turning a pneumatic node into an RNS transport means driving that engine
from the socket up. The realistic route is an application-layer gateway: a pneumatic
node with many links forwarding `Message` envelopes byte-for-byte, which preserves
end-to-end content auth, reuses the Gossiper's `(sender, body)` dedup as loop
prevention, and needs a hop limit on the *frame* (not the signed message) plus admission
and rate limits — none of which exist anywhere in `src/`.

Which is why the advice starts with the experiment rather than the design: set
`shard_count: 2` in a generated cluster's `env.json` and boot it. Nothing needs writing.
Whatever breaks is the real work list, in place of a design document written against
code that has never executed.

Kept for the archive: two probes were launched to map the rns crates and the routing
code; I verified both directly from source instead and interrupted the first, since a
summary of a file I had already read was worth less than the read.

Also worth naming: the ceiling we keep quoting (39 interfaces per node at 40 validators)
was inferred from *interface counts*, but with a 3796-byte hybrid signature every
message from every peer must verify, so a dense mesh is plausibly O(N²) verification-bound
before it is socket-bound — and relay does nothing for that. Measuring which resource
breaks first should precede choosing between the two levers.
