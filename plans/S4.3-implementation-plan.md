# Phase S4.3 Implementation Plan — `MerkleRootState` (Merkle-root freshness)

> Expanded, actionable implementation plan for **Phase S4.3** of
> [`pneumatic-shielded-implementation-plan.md`](pneumatic-shielded-implementation-plan.md)
> (the "Merkle-root freshness" item in Phase S4, parent plan :657-667).
>
> Scope: the **concrete committed-root history** the merkle-root freshness
> check (S4.1 check 3) reads, plus the K recency window as an environment
> consensus parameter. S4.3 builds the data structure the freshness check
> consumes: S4.1's check 3 *reads* it (via the `MerkleRootHistory`
> interface S4.1 defined, validation.rs:413-416), S5.1 (sentinel), S5.2
> (finalizer) and S5.3 (committer) *advance* it. What S4.3 deliberately does
> **not** do — persistence, the single-writer guard, the load-at-boot
> rebuild, the rollback interaction — is S5.3's `ShieldedPool` job; the
> scope boundary is stated in *Decision 5*.

## 1. Context & what S4.3 delivers

Roadmap 2.5 locks the pool root history as consensus-critical: every node
must agree on *which referenced roots are fresh*. The parent plan's S4.3
item specifies:

- `src/shielded/` (root state) + `src/validation.rs` (the check). The check
  **already exists** — S4.1 built check 3 (`is_root_fresh`,
  validation.rs:511-525) against the `MerkleRootHistory` trait, so this
  item's `src/validation.rs` half is *test-module only* (the concrete-type
  discriminator re-run), not production code. See *Decision 4*.
- The pool root only advances as commitments land in committed blocks
  (S5.3's guarded `apply_pool_update`). A shielded tx references the root it
  was proved against (`ShieldedTransaction.merkle_root`, S3.1). Accept if
  the referenced root equals the current root **or lies within the last K
  committed pool states**; K configurable, default small (e.g. 10); older →
  `StaleMerkleRoot`, fail-closed.
- The K window **mirrors the Phase 3.4 orphan buffer's tolerance** for
  near-tip state (bounded, per-token-lag-absorbing) — the structural
  analogy is carried into the type (bounded retention, *Decision 1*).

### Deliverables

- `MerkleRootState` + the six-method API (`src/shielded/roots.rs`, new
  module) with the consensus-critical / append-only / bounded / genesis-
  seeded doc comments; re-exported from `src/shielded/mod.rs`.
- `impl MerkleRootHistory for MerkleRootState` — closes S4.1's interface
  seam (the S4.1 plan's Open item 6: "S4.2/S4.3 must re-run those same
  discriminators against the concrete implementation"; the S4.2.4 precedent
  for the check-2 side stands).
- The S4.1 check-3 discriminator re-run **against the concrete state**
  (build item S4.3.3), including the parent item's exact verify list:
  current accepted, K-1-back accepted, K+1-back rejected, and the **K=0
  discriminator** (window logic, not equality).
- K as a consensus parameter: `shielded_root_recency` in
  `EnvironmentMetadataSpec` (serde default 10) + `EnvironmentMetadata`
  (build item S4.3.2).
- The genesis-bootstrap property (a first transfer proved against the empty
  pool root passes freshness on a fresh network), build item S4.3.4.

### Ground rules applied

- **Additive only.** One new module + one re-export line + one env-spec
  field (with `#[serde(default)]`) + eight test-only struct-literal updates
  the compiler enforces. No `Transaction` / `SignedTransaction` /
  `ShieldedTransaction` field, no action string, no wire change of any kind
  (see *Wire-compat note*).
- **Fail closed.** Unknown root, pruned root, and empty-history views all
  reject with the exact structured reason S4.1 check 3 surfaces
  (`StaleMerkleRoot`, errors.rs:164) — never a silent accept, never a
  panic. `push` is infallible *by contract* (it is called only under S5.3's
  guard with a genuinely new root) — the type documents that, and S4.1
  check 1 (non-empty, pairwise-distinct commitments) is the upstream guard
  that makes every `push` a strict root advance.
- **Existing behavior untouched.** Check 3 and `is_root_fresh` are not
  modified (S4.1's code stands — the window math is already exactly the
  parent item's spec); `FakeRootHistory` and every existing test pass
  byte-identical.

## 3. Design decisions (the meat of S4.3)

### Decision 1 — A bounded, append-only `MerkleRootState`; pruning is
lossless **iff** all nodes share K

```rust
/// Bounded, append-only history of committed pool roots.
#[derive(Debug, Clone)]
pub struct MerkleRootState {
    /// The recency window this state retains (the consensus K).
    window: usize,
    /// Oldest → newest. At most `window + 1` entries, never empty
    /// (seeded with the genesis pool state at construction).
    roots: Vec<RootSnapshot>,
}

impl MerkleRootState {
    pub fn new(recency_window: usize) -> Self;        // genesis @ height 0
    pub fn push(&mut self, root: [u8; 32]) -> u64;    // append tip, prune to window+1
    pub fn current_root(&self) -> [u8; 32];           // never None (genesis)
    pub fn recency_window(&self) -> usize;
    pub fn len(&self) -> usize;
    pub fn is_empty(&self) -> bool;                   // always false (documented)
}
```

**Bounded to `K + 1` entries, mirroring the Phase 3.4 orphan buffer.**
After every `push`, the state retains exactly the newest `window + 1`
snapshots (distances 0..=K behind the tip). At the default K = 10 that is
11 × 40 B = **440 B** — versus 40 B per committed shielded block growing
forever in an unbounded history. The boundedness is the parent item's
"mirrors the orphan-buffer's tolerance" carried into the type: the window
exists to absorb near-tip view lag (per-token chain interleave; split-
deployment replay lag, S5.1 :719-724), and the state retains exactly the
states that tolerance can ever reference — nothing more.

**Why retaining exactly K+1 changes no acceptance (the losslessness
argument — load it, then state it in the type's doc comment):** a referenced
root is fresh iff (a) it occurs in the committed history and (b) it is at
distance ≤ K from the tip. Any snapshot older than distance K is
**rejected by (b) on every node** — so dropping it from retention cannot
turn a reject into an accept, on **any** node. The one caveat: a node
running a *larger* K than its peers would consider some pruned-elsewhere
roots fresh. Therefore the bounded retention is sound **iff all nodes agree
on K** — which is exactly why K is a *consensus parameter* (Decision 3),
not per-node policy. The K-agreement requirement is what makes the orphan-
buffer-style boundedness safe here; the two decisions are load-bearing
together.

**Invariants (documented on the type):**

- **Append-only; the only removal is the internal window prune** inside
  `push` (keep newest `window + 1`). No rewind/rollback/trim API of any
  kind — the rollback interaction is S5.3's design question (Decision 5,
  Open item 3), and S4.3 builds no dangerous method for it, mirroring S4.2's
  Decision 3.
- **Consecutive snapshots have distinct roots.** Every applied pool update
  appends ≥ 1 commitment, so the tree root strictly advances; the upstream
  guard is S4.1 check 1 (non-empty, pairwise-distinct commitments) plus
  S5.3's guarded apply. Distinctness makes the root→height lookup inside
  `is_root_fresh` unambiguous within the window.
- **Heights are a 0-based pool-update sequence number, not chain block
  heights** (the pool is global; per-token chains interleave — S5.3
  :815-817). `push` returns the new tip's height.
- **`Send + Sync`** (plain `Vec` + `usize`; no interior mutability) so S5.3
  can `Arc`-share the state exactly as it shares `NullifierRegistry` —
  pinned by a compile-time test (S4.3.1).

**Consequence for the reject side (stated so S4.3.3's tests read correctly):**
on a bounded state, "referenced root is more than K back" and "referenced
root is not in the history" are the *same event* — the prune already
removed it — so the `distance > K` arithmetic branch of `is_root_fresh` is
structurally unreachable for this type; such references fail closed via the
`None` arm (validation.rs:523). The arithmetic itself is **not**
untested: S4.1.5's fake-based discriminator
(`root_freshness_accepts_within_window_and_rejects_beyond`,
validation.rs:1623) keeps it pinned on a full-history view where the
distance comparison is the deciding factor, and S4.3.3's boundary test
(reference at exactly distance K → accepted) exercises it on the concrete
type, where a present root at distance K is accepted *only if* the check is
`<=`, not `<`. If a future `MerkleRootHistory` implementation retains a
longer history (e.g. S5.1's replay view keeping extra context), the
arithmetic branch simply becomes load-bearing for it — no change needed;
the check is already correct.

### Decision 2 — Genesis seed: the empty pool root is a valid reference
target from the first block

`MerkleRootState::new(k)` seeds
`RootSnapshot { root: root_to_bytes(&Fp::zero()), height: 0 }` — the empty
tree's root (S1.6: `IncrementalMerkleTree::root()` is `Fp::zero()` at zero
leaves, tree.rs:215-221), i.e. 32 zero bytes.

- **Why:** on a fresh network the first shielded transfer must be provable
  against *some* root, and the only well-defined candidate is the empty
  pool root. Seeding it at construction makes the genesis entry identical
  on every node by construction, so the first tx's referenced root verifies
  deterministically everywhere. Without the seed, a fresh state's history
  is empty, `is_root_fresh` returns false on the `is_empty` arm, and the
  first transfer is rejected — a bootstrap deadlock.
- **The empty-history fail-closed arm stays** (validation.rs:516-519):
  unreachable for this type (genesis guarantees non-empty) but it remains
  the trait contract's defense-in-depth for any other `MerkleRootHistory`
  implementation and for any future corrupted/degenerate view.
- The genesis entry also **anchors the height numbering at 0**, so the
  "distance from tip" math in `is_root_fresh` is exact from the first
  update.

### Decision 3 — K is a consensus parameter in the environment spec
(default 10; `validate()` deliberately untouched)

```rust
// EnvironmentMetadataSpec (environment.rs:273-296)
/// Shielded Merkle-root recency window (S4.3): a referenced pool root is
/// fresh if it is at most this many committed pool states behind the tip.
/// **Consensus parameter** — every node in the environment must run the
/// same value (S5.3 step 3). Divergence means per-node acceptance
/// divergence — a deployment error, not a code defect.
#[serde(default = "default_shielded_root_recency")]
pub shielded_root_recency: usize,

fn default_shard_count() -> u32 { 1 }                    // :298 — the idiom mirrored
fn default_shielded_root_recency() -> usize { 10 }

// EnvironmentMetadata (environment.rs:126-161)
pub shielded_root_recency: usize,

// load_from_spec (field copy alongside :258 / :267-268)
shielded_root_recency: spec.shielded_root_recency,
```

- **Default 10** per the parent item ("K configurable, default small, e.g.
  10"). The `#[serde(default = "…")]` idiom is the production-proven
  `shard_count`/`shard_quorum_percentage` pattern
  (environment.rs:290-299): old env-spec JSON (no key) parses unchanged and
  resolves to 10. No repo-tracked env-spec JSON exists (specs load from
  `/env/` at runtime), so nothing else to update.
- **`validate()` is intentionally unchanged.** It gates *protocol-breaking*
  values (0% quorum, >100%, non-finite multipliers). `usize` is
  non-negative by type; **no** K value neuters the protocol at boot — K=0
  is the strictest legal policy (exact-tip only), and a large K merely
  weakens staleness tolerance, which is operator policy in the same
  category as the Phase 3.4 orphan buffer's capacity (also a plain config
  value with no `validate()` check). The one hazard that *is* real —
  cross-node divergence — is structurally invisible to a per-node
  `validate()`, so a check there would be false comfort; the hazard is
  documented on the field and carried as Risk 1. (Open item: the roadmap
  owner may add a hard upper bound in a future phase — a K = u32::MAX
  config would render freshness nearly meaningless; v1 ships the default +
  documentation, no cap.)
- **The spec stays stateless:** S5.1's sentinel (and S5.3's committer)
  read `env.shielded_root_recency` into
  `ShieldedValidationDeps.recency_window` at call time. `K` appears in
  `MerkleRootState` only as its *retention* parameter (Decision 1) — the
  two K's are the same number, threaded from the same env field, so a
  node's retained history and its acceptance window cannot drift apart.

### Decision 4 — The check is already built (S4.1); S4.3 closes the seam,
with **zero** production changes to `validation.rs`

Check 3 and `is_root_fresh` (validation.rs:511-525, 567-570) were built by
S4.1 *against the trait* on purpose — "the check is buildable and testable
before the concrete type exists" — and the window math S4.1 wrote
(`newest.height - idx.height <= recency_window`, empty → false, unknown →
false) is **exactly** the parent item's spec ("accept if equal to the
current root OR within the last K committed pool states … older →
`StaleMerkleRoot`, fail-closed"). S4.3 therefore:

1. implements `MerkleRootHistory for MerkleRootState` (one method: return
   `&self.roots` — oldest→newest, last = tip, the trait contract at
   validation.rs:414), and
2. **re-runs S4.1's check-3 discriminators against the concrete type**
   (the S4.1 plan's Open item 6; the S4.2.4 precedent, where the check-2
   re-run lived in `validation.rs`'s test module next to the shared
   fixtures).

The parent item's "Files: `src/validation.rs` (the check)" refers to the
check's home — S4.1 already delivered it. This phase touches
`validation.rs` **test module only**.

### Decision 5 — Scope boundary with S5.3's `ShieldedPool`

S4.3 is the **in-memory read-side root state** — the exact mirror of what
S4.2 did for the nullifier set. The parent plan assigns to S5.3 the
single-writer guard (:818-819), durability (:873+), load-at-boot
fail-closed, and rollback unwind (:865-872). Therefore S4.3:

- **Does not** take external locks, does not persist, does not load at
  boot, and exposes **no rewind/rollback API**. (S5.3's pool wraps
  `Arc<MerkleRootState>`; the state is `Send + Sync` — Decision 1 — so the
  `Arc` sharing is free, as for `NullifierRegistry`.)
- **Does not** define `ShieldedPool`, the applied-update map, or any
  committer code.
- **Does** keep the API shape S5.3 needs: `push` is the step-4 primitive —
  inside `apply_pool_update`, after commitments are appended, S5.3 pushes
  the post root computed from its own tree, under the pool guard
  (the committer computes the post root; the block does not assert it —
  S5.3 :844-849).
- **Does** document on the type that the history is a **derived, bounded
  view** — not a fourth persistent element. The parent's S5.3 bullet lists
  exactly three held structures: (a) the Merkle tree, (b) the nullifier
  set, (c) the applied-update map (:818-823) — the root history is
  *reconstructable* from (a)+(c): every snapshot in it is "the tree root
  after applying some prefix of the applied-update map". S5.3's
  load-at-boot procedure is: rebuild `MerkleRootState::new(
  env.shielded_root_recency)`, replay the applied-update map in order
  pushing each post root, then **fail closed** if
  `current_root() != tree.root()` (history/tip divergence = corrupted
  state). That contract is S5.3's to implement; S4.3 documents it here so
  the boundary is explicit (Open item 2).
- **Does** document the rollback interaction as *unsettled* (Open item 3):
  when `resolve_block_conflict()` rolls the tip back (:865-872), the loser
  block's root snapshot must leave the tip — but an append-only, prune-only
  type has no rewind method for S5.3 to call, exactly as S4.2's registry
  has no un-mark. S5.3's plan must define the root-history effect of a tip
  rollback explicitly (the natural candidate is: truncate the history to
  the pre-loser tip, then re-advance with the winner's post root — the
  inverse of `push`), with roadmap 2.5 cited. S4.3 is neutral on the call
  and builds nothing for it.

## 5. Wire-compat note (ground rule 4)

**No wire change of any kind.** `MerkleRootState` is node-local consensus
state:

- No new action string, no new payload schema, no new message.
- No field added to `Transaction`, `SignedTransaction`, or
  `ShieldedTransaction` — the referenced root already rides the wire as
  `ShieldedTransaction.merkle_root` (S3.1); this phase only decides,
  per-node, which referenced roots are *fresh*.
- The root history is not gossiped: it is replicated **by replay** — every
  node derives it deterministically from committed block history (S3.1:
  the pool update is hash-bound inside `signed_trans.shielded`; S5.1
  :719-724), and the K-recency window absorbs split-deployment view lag —
  the same replication story as S4.2's nullifier set.
- Old nodes see no difference (they already fail closed on
  `"ShieldedTransfer"` per S3.2); new→old / old→new decode paths are
  untouched.
- The only observable wire-adjacent behavior is *rejection semantics*:
  references beyond the window are rejectable with the exact
  `StaleMerkleRoot` reason — which S4.1 already introduced as an additive
  serde-tagged enum variant (its own wire note stands; this phase adds no
  variant).
- **One config-schema addition (not wire):** the environment spec JSON
  gains an *optional* key `shielded_root_recency` (default 10) via
  `#[serde(default)]` — old env specs parse byte-identically (no
  repo-tracked env JSON; runtime `/env/` specs covered by the S4.3.2
  `VALID_BASE` test). Deployment note: an environment wanting a
  non-default K must set the key explicitly in its env spec — and, per
  *Decision 3*, **every** node in that environment must then run the same
  value (consensus parameter; Risk 1).

## 6. Risks & open items

1. **HEADLINE — K divergence = split brain (Decisions 1+3).** A node
   running a different K than its peers accepts and retains a different
   set of referenced roots: with a *smaller* K it prunes roots its peers
   still accept; with a *larger* K it accepts roots peers reject. The env
   spec is per-node config, and no per-node `validate()` check can see a
   cross-node disagreement — the same exposure class as every other
   consensus-valued env field (quorum percentages etc.), enforced by
   deployment process, not code. v1: documented on the field + default
   10 + the S4.3.2 tests. **Flag to roadmap owner:** consider a hard
   upper bound on `shielded_root_recency` in a future phase (a
   K = u32::MAX config would render freshness nearly meaningless).
2. **The root history is derived state — S5.3 must rebuild it at load and
   cross-check the tip (Decision 5).** The parent's S5.3 pool holds three
   persistent structures (tree, nullifiers, applied-update map); the root
   history is reconstructed from them, then a
   `current_root() == tree.root()` fail-closed assertion guards
   history/tip divergence at boot. S5.3's plan must state the rebuild
   procedure; S4.3's contract is the documented one in Decision 5.
3. **Rollback/rewind interaction is unsettled (Decision 5; pairs with the
   S4.2 plan's Open item 1).** The S5.3 conflict path (:865-872) rolls the
   tip back; the loser block's root snapshot must leave the tip, but S4.3
   deliberately exposes no rewind API (append-only + prune only, mirroring
   S4.2's no-un-mark). S5.3's plan must define the root-history effect of
   a tip rollback explicitly — recommended: truncate the history to the
   pre-loser tip, then re-advance with the winner's post root (the inverse
   of `push`) — with roadmap 2.5 cited. Decide before S5.3 starts; S4.3
   is neutral on the call and builds nothing for it.
4. **The "beyond window" branch is unreachable on the bounded type (by
   design, Decisions 1/4).** Acceptance on a bounded state reduces to
   "present and distance ≤ K", and presence already implies distance ≤ K;
   the comparison arm is pinned by S4.1.5's fake-based tests (full
   history) + the S4.3.3 boundary test (distance exactly K on the concrete
   type). If a future `MerkleRootHistory` implementation retains a longer
   history (e.g. S5.1's replay view), the arithmetic branch becomes
   load-bearing for it with no change needed.
5. **Two "K"s.** `SHIELDED_VK_K: u32 = 10` (validation.rs:394) is the
   Halo2 *instantiation width* the `ActionCircuit`/`ShieldedVerifier` are
   built at; the recency K is `recency_window: usize` /
   `shielded_root_recency` (default 10). Both happen to be 10; they are
   unrelated numbers. Documented here and in the type/spec doc comments to
   prevent a future "tidy-up" from unifying them.
6. **No live-prove in this phase** — the five accept-side seam tests
   (S4.3.3 ×5 incl. S4.3.4) reach check 4 and reuse S4.1's
   `Lazy<ShieldedVerifier>`; if S4.1's keygen cost ever moves the core-lib
   binary's run time, it moves with S4.1's tests, not this phase's.
