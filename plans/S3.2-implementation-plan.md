# Phase S3.2 — Message Wiring: Implementation Plan

> Companion to `pneumatic-shielded-implementation-plan.md` (Phase S3.2). This
> document breaks that checklist entry into concrete, ordered implementation
> tasks, grounded in the *actual* code across `sentinel`, `finalizer`,
> `node-server`, and `pneumatic_core`. It records what the plan stub leaves
> implicit (notably: **the handler bodies are S5.1/S5.2 — S3.2 only wires the
> action strings + the fail-closed gate**, and how to keep `cargo check` green
> while doing so).

## 0. One-paragraph scope

S3.2 registers the **three shielded action strings** on the inbound dispatch
paths so a shielded transaction can be *routed* through the pipeline:

- `"ShieldedTransfer"` — client → Sentinel (inner action under the `"Verify"`
  envelope),
- `"SignShielded"` — Sentinel → Finalizers (vote request carrying the
  `ShieldedTransaction`),
- `"ShieldedVote"` — Finalizer → collector Finalizer (a `TransactionSignature`
  vote).

S3.2 is **pure wiring**: it adds the `match` arms, the role `allowed_actions`
entries, and the fail-closed gate — **not** the handler logic. The handler
bodies (`handle_shielded_transfer`, `handle_sign_shielded`,
`handle_shielded_vote`) are **S5.1/S5.2**. This document's key
decision/recommendation (Section 5) explains how S3.2 stays self-contained and
keeps the workspace build green ahead of S5.

The single consistency property S3.2 must preserve: **an action not owned by a
role is rejected, never silently accepted** (Ground Rules 4–5). That gate is
already implemented in `RoleDispatcher::dispatch` and the sentinel's/finalizer's
existing `UnknownAction` / else-fail-closed arms — S3.2 leans on them, it does
not re-implement them.

## 3. Ground-truth wiring map (corrects the plan stub)

The plan stub listed `src/messages.rs (action constants, if any)` and
`finalizer/src/message_dispatcher.rs (outbound helpers)`. Ground truth:

- **`src/messages.rs` has NO action constants.** Every action in the codebase is
  an ad-hoc string literal (`"Process"`, `"Sign"`, `"Commit"`, `"BlockFinalized"`,
  …). `Message` is a plain `{chain_id, action, body, signature, public_key,
  stake_set}` struct (`messages.rs:10-26`), and the signing helper is
  `Message::signed(chain_id, action: &str, body, stake_set, identity)`
  (`messages.rs:47-63`). **Decision: do NOT introduce constants in messages.rs**
  — the three new strings stay ad-hoc literals, consistent with the entire
  existing codebase and the minimal-diff principle. (If the team later wants
  named constants to guard against typos, that is a separate refactor; not now.)
- **The production Finalizer inbound path is `node-server` only.** `handle_signature`
  (finalizer.rs:346) is invoked from `node_server.rs:645` (the composite
  Finalizer plugin's `handle` match). The `finalizer` crate has **no** standalone
  inbound `action` match — there is no separate dispatcher to update for a split
  deployment in this codebase. So the Finalizer-side S3.2 wiring is entirely in
  `node_server.rs` (`FINALIZER_ACTIONS` + the `handle` match).
- **Sentinel outer envelope stays `"Verify"`.** The composite Sentinel plugin
  (`node_server.rs:613-623`) calls `self.on_data_received(message.body)` and
  **ignores the outer `action`** — the outer action is already gated to
  `"Verify"` by `SENTINEL_ACTIONS` (node_server.rs:41) in the dispatcher. So the
  new arm goes in `on_data_received`'s **inner** `message.action` match
  (sentinel.rs:114-122), and **`SENTINEL_ACTIONS` is unchanged**.
- **`message_dispatcher.rs` is not modified in S3.2.** Its outbound helpers
  (`send_block_finalized`, `send_block_confirmed_vote`, …, message_dispatcher.rs:
  108-213) are the model for the S5.2 builders `send_sign_shielded` /
  `send_shielded_vote`, but those are S5.2 work. The Sentinel builds the
  `"SignShielded"` message itself via `Message::signed("SignShielded", …)`
  (S5.1); S3.2 only registers the string on the *inbound* side.
- **Vote payload type is `TransactionSignature`** (the existing voter
  `handle_signature` deserializes it, finalizer.rs:348). `"ShieldedVote"` rides
  the same struct — no new wire type (matching the doc's "no new wire struct").

## 4. Wire-compat guarantees (Ground Rule 4 — must hold, proven by tests)

1. **No message-shape change.** `Message` (`messages.rs:10-26`) is untouched; the
   three new actions are new **values** of the existing `action` field, not new
   fields. The 4-byte-length-prefixed MsgPack framing is unchanged.
2. **Inner-body shape for `"ShieldedTransfer"` is identical to `"Process"`.** In
   the composite node the client sends an outer `Message{action:"Verify",
   body: rmp(Message{action:"ShieldedTransfer", body: rmp(ShieldedTransaction)})}`
   — the sentinel's `on_data_received` deserializes `message.body` as a `Message`
   and matches on its inner action, exactly as it does for `"Process"` today
   (sentinel.rs:111-114). No envelope change.
3. **Old nodes fail closed.** A pre-upgrade node sees `"SignShielded"` /
   `"ShieldedVote"` / `"ShieldedTransfer"` as unknown actions and rejects them
   via the existing gates (`RoleDispatcher::UnknownAction`, the sentinel's
   `UnknownAction` arm, the finalizer's else-fail-closed arm) — never a silent
   accept (Ground Rule 5). No upgrade dance required.
4. **Non-shielded paths byte-identical.** No existing `match` arm's bytes change;
   the new arms are additional. The existing `blocks.rs` hash tests and all
   sentinel/finalizer routing tests pass untouched (regression guard).

## 5. The central decision — keep the build green before S5

S3.2 adds `match` arms, and a `match` arm must route to an existing function. But
the real handler bodies live in S5.1/S5.2. If S3.2 adds the arms and stops there,
the crate **does not compile** (unresolved `handle_shielded_transfer`, etc.).
Ground Rule 1 requires `cargo check` + full `cargo test --workspace` green after
*every* item.

**Recommended approach — S3.2 wires the gate + stubs; S5 replaces the bodies.**

Add the three arms, each routing to a **minimal stub handler** that:

- **deserializes the inner payload** (so the wire path is exercised and a bad
  body fails closed with `Encoding`), and
- **returns a fail-closed `Err`** (a clearly-marked "not yet wired" protocol
  error).

The stubs are the *only* body work in S3.2; S5.1/S5.2 delete the stub and drop in
the real implementation **without touching the arm or the `FINALIZER_ACTIONS`
entry**. This keeps S3.2 self-contained and the workspace green, and it matches
the plan doc's file list (which names the arms).

**Alternative (Option B) — defer the arms to S5.** Restrict S3.2 to `FINALIZER_ACTIONS`
+ the fail-closed gate + the wire-roundtrip test, and add the sentinel/finalizer
arms together with their real handlers in S5.1/S5.2. Cleaner (no stubs), but it
deviates from the plan doc's explicit file list and pushes the "arm" work into
S5. Recommend **Option A** above unless the team prefers no stubs.

The stub error choice (minor): reuse existing fail-closed variants — the sentinel
stub returns `SentinelError::Routing("shielded transfer pipeline not wired yet")`
(or a new `SentinelError::NotWired` variant if preferred); the finalizer stubs
return `PneumaticError::Network("shielded pipeline not wired yet")`. Both are
already-used, non-panicking, fail-closed error paths. The exact variant is
immaterial — S5.2 replaces the body.

### S3.2 stub reference (illustrative — Option A)

`sentinel/src/sentinel.rs` — new arm (sentinel.rs:114-122) + stub:

```rust
// in on_data_received's match:
"ShieldedTransfer" => self.handle_shielded_transfer(message),

// stub — replaced wholesale by S5.1 (validation, token lookup,
// shielded_transactions registry, send-to-finalizer). S3.2 only proves the arm
// exists, the inner body deserializes, and the path fails closed.
fn handle_shielded_transfer(&self, message: Message) -> Result<(), SentinelError> {
    let _tx: ShieldedTransaction = deserialize_rmp_to(&message.body)
        .map_err(|e| SentinelError::Encoding(e))?;
    Err(SentinelError::Routing(
        "shielded transfer pipeline not wired yet (S5.1)".to_string(),
    ))
}
```

`node-server/src/node_server.rs` — `FINALIZER_ACTIONS` (node_server.rs:43) + arms:

```rust
// node_server.rs:43
const FINALIZER_ACTIONS: &'static [&'static str] =
    &["Sign", "Finalize", "SignShielded", "ShieldedVote"];

// finalizer RoleHandler::handle match (node_server.rs:640-656)
match message.action.as_str() {
    "Sign" => self.handle_signature(&message).await.map(|_| ()).map_err(…),
    "SignShielded" => self
        .handle_sign_shielded(&message)
        .await
        .map(|_| ())
        .map_err(|e| RoleError::Downstream(PneumaticError::Network(format!("{e:?}")))),
    "ShieldedVote" => self
        .handle_shielded_vote(&message)
        .await
        .map(|_| ())
        .map_err(|e| RoleError::Downstream(PneumaticError::Network(format!("{e:?}")))),
    other => Err(RoleError::Downstream(PneumaticError::Network(format!(
        "finalizer: unhandled inbound action {other:?}"
    )))),
}
```

## 6. Discriminator tests (one per requirement; each fails without its change)

Per the AUDIT_CHECKLIST ground rules, each is proven by temporarily reverting the
corresponding code and watching it fail.

1. **`shielded_message_wire_roundtrip`** (`src/messages.rs` or a new
   `node-server`/`sentinel` test) — build `Message::signed("env", "SignShielded",
   rmp(ShieldedTransaction), None, &identity)`, serialize with the existing
   length-prefixed framing, deserialize, and assert: `action == "SignShielded"`,
   the body recovers a `ShieldedTransaction` with the same `hash()`, and the
   signature verifies. Proves the wire path for a shielded payload works end to
   end over the unchanged framing. **Discriminator:** tamper one byte of the body
   → `hash()` mismatches / verification fails (fail closed, not a silent accept).
2. **`role_dispatcher_routes_signshielded_to_finalizer`** (`role_dispatcher.rs`,
   using the existing `SpyHost` scaffold, lines 193-265) — a Finalizer `SpyHost`
   whose `allowed_actions` include `"SignShielded"`/`"ShieldedVote"`; assert
   `dispatch(Message{action:"SignShielded"})` is routed (recorded), not rejected.
   Proves the role-map now admits the new actions.
3. **`role_dispatcher_rejects_shielded_action_when_absent`** — **the plan's
   discriminator (load-bearing gate).** A Finalizer `SpyHost` that does **not**
   list `"SignShielded"` in its actions; assert `dispatch` returns
   `RoleError::UnknownAction("SignShielded")`. Removing the entry ⇒ rejection,
   proving the gate is real, not cosmetic. (This is the ground-truth mirror of the
   doc's "remove the role-map entry → the message is rejected.")
4. **`node_server_finalizer_signshielded_reaches_real_plugin`** (`node-server`
   integration, using the `route_data_plane` + `build_runtime` scaffold, lines
   750-1070) — a `route_data_plane` call with a `"SignShielded"` message and an
   installed Finalizer; assert it reaches the **real** Finalizer plugin's
   `handle` (i.e. the stub ran and returned the "not wired yet" error, proving the
   message traversed the dispatcher → plugin → match arm). This pins the composite
   routing for the new action.
5. **`sentinel_on_data_received_shieldedtransfer_arm_reaches_handler`**
   (`sentinel/src/sentinel.rs`) — feed `on_data_received` the inner
   `Message{action:"ShieldedTransfer", …}`; assert it reaches the arm (the stub's
   `Routing("… not wired yet")` error is returned), proving the arm routes the
   inner action and does not fall through to `UnknownAction`. **Discriminator:**
   comment out the arm ⇒ the same input now returns `UnknownAction("ShieldedTransfer")`
   (proves the arm is load-bearing).

Tests **1 and 3 are the headline discriminators** (wire roundtrip + load-bearing
gate), matching the plan doc's Verify section exactly.

## 9. Risks & open points

- **Stub-vs-real-body ownership.** The whole reason S3.2 exists as a discrete,
  green-buildable item is the stub convention in Section 5. If S5.1/S5.2 forget
  that the arms already exist, they may try to re-add them — the arms +
  `FINALIZER_ACTIONS` entries belong to S3.2; only the *bodies* are S5.
- **Composite vs split deployment.** The Finalizer inbound path in this codebase
  is `node-server` (composite) only — confirmed: the `finalizer` crate has no
  standalone action match. If a future split deployment adds one, it must also
  register these actions (fail-closed). Flag to S5.4 if split deployment is in
  scope.
- **Action-string typos.** Without named constants (Section 3), a typo in
  `"SignShielded"` on the send side vs. the receive side is a silent no-match
  (the receiver fails closed with `UnknownAction`, which is safe, but the tx is
  dropped). Acceptable for v1; consider named constants as a follow-up, not now.
- **Note-ciphertext sizing.** A typical 2-in/2-out transfer carries ~4.6 KB of
  PQC-hybrid note ciphertexts inside the body — well under the 16 MiB frame cap,
  but worth one assertion in the wire-roundtrip test (Section 6, test 1) so a
  future regression in framing is caught early.
- **No validation in S3.2.** The sentinel `"ShieldedTransfer"` arm returns an
  error (stub) — it does **not** run `ShieldedValidationSpec` (S4.1/S5.1) or do
  token lookup. Do not mistake the stub's fail-closed for the real advisory
  pre-check; S5.1 adds it.
