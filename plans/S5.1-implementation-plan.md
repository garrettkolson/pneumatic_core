# Phase S5.1 Implementation Plan — Sentinel: shielded routing branch

> Expanded, actionable implementation plan for **Phase S5.1** of
> [`pneumatic-shielded-implementation-plan.md`](pneumatic-shielded-implementation-plan.md)
> (the "Sentinel: shielded routing branch" item in Phase S5, parent plan
> :688-730).
>
> Scope: the **sentinel-side entry point** for shielded value transfer. S3.2's
> fail-closed stub (`handle_shielded_transfer`, sentinel.rs:143-149) becomes the
> real five-step path: canonical-rmp deserialize → advisory
> `ShieldedValidationSpec` pre-check (S4.1) → token lookup (self-verified +
> shielded opt-in) → atomic registration in a parallel `shielded_transactions`
> map → deterministic finalizer assignment + `SignShielded` to the finalizer
> set — **bypassing Executor/preload entirely** (roadmap 2.1). Plus the read-only
> **pool-view seam** (`ShieldedPoolView` + `SimpleShieldedPoolView` placeholder)
> the sentinel needs for the pre-check, and the composite node's placeholder
> wiring. What S5.1 deliberately does **not** do — the `ShieldedPool` itself,
> the single-writer guard, persistence, load-at-boot, rollback, the
> `SignShielded` vote handler, the split-deployment replay loop — is S5.2/S5.3/
> S5.4's job; the scope boundary is stated in *Decision 1* and §7.

---

## 1. Context & what S5.1 delivers

The shielded pieces built so far are all **independent**: S4.1's spec validates
a `ShieldedTransaction` against a pool view *if someone hands it one*; S4.2's
`NullifierRegistry` and S4.3's `MerkleRootState` are data structures with no
caller outside their own tests. S5.1 is the first phase that puts a shielded
transfer **in motion through the network**: a client-shaped
`"ShieldedTransfer"` message now exits the sentinel as a `"SignShielded"`
message aimed at an assigned finalizer, with every gate the parent item
specifies (:695-714) in between.

The parent item specifies (verbatim abridged):

1. Deserialize `ShieldedTransaction` from the inner body (encoding error →
   fail-closed `Encoding`).
2. Run `ShieldedValidationSpec` (S4.1) — **advisory pre-check**: it rejects
   obvious garbage (bad proof, already-spent nullifier, stale root) before any
   finalizer work, but is **NOT the consensus gate** — the authoritative
   re-check is the committer's guarded apply (S5.3).
3. Token lookup: `token_id` must reference an existing, `is_self_verified`,
   shielded-opt-in token (fail-closed `TokenNotFound` / `NotSelfVerified`).
   The sentinel does **not** fetch token data for the *amount* — it has no
   balance data to check and none is revealed.
4. Register in a new parallel map on `PendingTransactionRegistry`:
   `shielded_transactions: DashMap<String, ShieldedTransaction>` (mirrors the
   `used_nonces` side-map pattern; **never evicted** — the committer's
   H12-style hash match, S5.3, compares against it). No new
   `TransactionState` variant: shielded txs are not `Transactions` and do not
   ride the `Pending → … → Committed` state machine.
5. Send `Message::signed("SignShielded", shielded_tx_bytes)` to the finalizer
   set — the deterministic finalizer-assignment machinery picks the collector,
   same as standard txs.

And the **pool view** (:715-725): the sentinel needs the pool's nullifier set
+ root history for step 2. In the composite node (primary deployment) all
roles share one `Arc<ShieldedPool>` (S5.3) from `build_runtime`; in split
deployments each role replays committed block history to maintain a local view
(the update is hash-bound inside `signed_trans.shielded`, S3.1 — deterministic,
no extra sync message; the K-recency window absorbs view lag).

### Deliverables

- `ShieldedPoolView` trait + `SimpleShieldedPoolView` concrete view
  (`src/shielded/pool_view.rs`, new module) — the single read-only seam every
  shielded role depends on (*Decision 1*).
- `PendingTransactionRegistry`: parallel `shielded_transactions` map +
  idempotent atomic `register_shielded` + getter (*Decision 5*).
- `Token::is_shielded_opt_in()` fail-closed helper + the
  `shielded_opt_in` metadata key + additive
  `ValidationFailureReason::NotShieldedOptIn` (*Decision 4*).
- `Sentinel`: 7th constructor parameter `pool_view: Arc<dyn ShieldedPoolView>`
  (*Decision 2*), `SentinelError::Validation(PneumaticError)` variant, and the
  real `handle_shielded_transfer` replacing the S3.2 stub (*Decision 5*).
- `TransactionNotifier::send_sign_shielded` — the outbound
  `"SignShielded"` message, mirroring the existing `Preload` pattern.
- node-server: placeholder `SimpleShieldedPoolView` in the `build_runtime` DI
  bundle threaded to the Sentinel plugin (the one-line S5.4 swap site).
- The S3.2 stub discriminator test is **repurposed**: its arm-present
  discriminator is kept (arm removed ⇒ `UnknownAction`), its assertion changes
  from the stub's `Routing` message to the real path's fail-closed
  `Validation(TokenNotFound)` (no token in the bare fixture).

### Ground rules applied

- **Additive only.** One new core module + one re-export line, one registry
  map + three methods, one token helper, one additive serde-tagged error
  variant, one additive `SentinelError` variant, one notifier method, one
  required constructor parameter (compiler-enforced call-site updates at
  sentinel.rs:859, :898, :2078 and node_server.rs:492). No wire schema change
  (see *Wire-compat note*).
- **Fail closed.** Every step has an explicit rejection: undecodable body →
  `Encoding`; missing spec → `UnsupportedAction`; any advisory failure →
  `Validation(reason)` with the exact S4.1 reason; missing token →
  `TokenNotFound`; not self-verified → `NotSelfVerified`; not opt-in →
  `NotShieldedOptIn`; duplicate id → `TransactionAlreadyExists`; no registered
  finalizer → `NoTarget`. No silent accept, no `unwrap` on a network-shaped
  value, no panics on the handler path.
- **Advisory ≠ consensus.** The handler's accept is permission to spend
  finalizer compute, not a commitment. The S4.1 spec runs here exactly as it
  runs in the finalizer (S5.2 step 2) and the committer (S5.3 step 0) —
  same spec, same deps shape, each node against its **own** pool view; the
  committer's guarded apply is authoritative (Risk 2).
- **Existing behavior untouched.** The `"Process"` / `"Confirm"` / … arms and
  every existing sentinel routing test pass byte-identical; the
  `"ShieldedTransfer"` arm at sentinel.rs:128 is not touched — only the
  handler body it routes to.

## 3. Design decisions (the meat of S5.1)

### Decision 1 — One read-only seam: `ShieldedPoolView`

The sentinel needs exactly the two read sides the S4.1 spec already abstracts:
the nullifier set (`NullifierMembership`, validation.rs:407) and the root
history (`MerkleRootHistory`, validation.rs:413). S4.1's own doc
(validation.rs:418-421) promises the shape: "the composite node shares one
`Arc<ShieldedPool>` (S5.3) that implements both traits; split deployments
replay block history (S3.1 / S5.1) and expose it through the same traits."
S5.1 builds the S5.1 half of that promise:

```rust
// src/shielded/pool_view.rs (new module)
pub trait ShieldedPoolView: Send + Sync {
    /// The spent-nullifier set (S4.1 check 2).
    fn nullifier_set(&self) -> &dyn NullifierMembership;
    /// The committed-root history (S4.1 check 3).
    fn root_history(&self) -> &dyn MerkleRootHistory;
}

/// The S5.1 placeholder: a fresh pair of the S4.2/S4.3 structures, shared by
/// `Arc`. S5.4 swaps this construction site for the real `Arc<ShieldedPool>`;
/// the sentinel (and later the finalizer) never changes.
pub struct SimpleShieldedPoolView {
    nullifiers: Arc<NullifierRegistry>,
    roots: Arc<MerkleRootState>,
}
impl SimpleShieldedPoolView {
    pub fn new(recency_window: usize) -> Self;   // fresh registry + genesis-seeded state
    pub fn with(nullifiers: Arc<NullifierRegistry>, roots: Arc<MerkleRootState>) -> Self;
}
```

**Rationale.** (a) S5.3's `Arc<ShieldedPool>` implements the *same* trait —
S5.4's swap is one construction line in `build_runtime`, zero sentinel/finalizer
changes, and the trait's doc comment is the contract S5.3 implements against.
(b) Split deployments' replay view implements it with the same two methods —
the replay mechanism itself is out of scope (S5.4/S6), but the seam it must
fill is fixed now, so S5.4 cannot reshape the roles' dependencies. (c)
`Send + Sync` is pinned in the trait (compile-time assertion test) because the
view is shared across the sentinel's gossiper threads via `Arc`.

**Rejected alternative:** two `Arc<dyn …>` constructor parameters
(`nullifier_set`, `root_history` directly). It couples the sentinel to two
parameters that S5.3 collapses into one, and — worse — permits passing the
nullifier set and root history of *two different pools* to one sentinel, a
split-brain wiring bug the bundled type makes unrepresentable.

### Decision 2 — Required `pool_view: Arc<dyn ShieldedPoolView>`, not `Option`

`Sentinel::new` gains a **required** 7th parameter. The "no pool state
available" case does not need an `Option`: a sentinel constructed with a
pristine `SimpleShieldedPoolView` fails closed on its own — its root history
is the genesis seed (S4.3, Decision 2 there), so **any** non-genesis-root
transfer rejects with `StaleMerkleRoot` inside check 3, and the nullifier set
is empty. The S4.1 checks are the empty-view gate; `Option<Arc<…>>` would add
a second, redundant branch (`None → UnsupportedAction`) and — the real risk —
an `unwrap`/`expect` in the handler on a wiring the type no longer forces.

**Call sites updated (compiler-enforced, four total):** sentinel.rs:859 and
:898 (the two fixtures — the default fixtures pass
`Arc::new(SimpleShieldedPoolView::new(10))` so every pre-existing test keeps
its pristine-view behavior), sentinel.rs:2078 (direct `Sentinel::new` in the
epoch-advance test), node_server.rs:492 (the composite arm — gets the shared
DI view).

### Decision 3 — Spec lookup by `ShieldedValidationSpec::NAME`, never the wire string

The wire action is `"ShieldedTransfer"` (sentinel.rs:128); the spec is
registered under `ShieldedValidationSpec::NAME` = `"Shielded"`
(validation.rs:458, `register_shielded` :344). The handler therefore does:

```rust
let spec = self.env_data.transaction_validation_specs
    .get(pneumatic_core::validation::ShieldedValidationSpec::NAME)
    .ok_or_else(|| SentinelError::Validation(
        PneumaticError::Validation(vec![ValidationFailureReason::UnsupportedAction])))?;
```

This is the exact fail-closed shape of the `SelfSigned`-missing pattern
(transaction_validator.rs:57-62): a deployment that never opted into the
shielded spec (no `register_shielded`) rejects the transfer with
`UnsupportedAction` instead of panicking on a missing name or silently
falling back to another spec. Looking up by the constant (not the string
`"Shielded"`) means a future rename of the registration name can never
silently break the sentinel's lookup — the seam is a single
compile-time-checked reference.

### Decision 4 — Shielded opt-in: token metadata flag + additive error variant

Parent :702-703 requires the token to be "shielded-opt-in", but **no such flag
exists in code** (tokens.rs:18-43: `is_self_verified`, `is_non_transferable`,
`block_validation_spec_name`, free-form `metadata`). This plan defines it:

- **Key:** token `metadata` (the `HashMap<String,String>` at tokens.rs:22) key
  `shielded_opt_in`, value must be exactly the string `"true"`.
- **Helper:** `Token::is_shielded_opt_in(&self) -> bool` —
  `self.metadata.get("shielded_opt_in").map(|v| v == "true").unwrap_or(false)`.
  Fail closed: missing key, `"false"`, `"1"`, `"TRUE"` — anything but
  `"true"` — is off. The helper centralizes the key name so the convention
  lives in one typed place (the mint path that writes it and every reader).
  No new `Token` struct field: that would repeat the S4.3.2-style
  struct-literal churn across the workspace for a flag whose single production
  reader is this handler; metadata is already the established carrier for
  mint-time token options (the same map the mint path parses
  `is_self_verified`/`validator_name` from at tokens.rs:352/:357). A promoted
  struct field is a follow-up tidy-up, not an S5.1 requirement.
- **Rejection reason:** new `ValidationFailureReason::NotShieldedOptIn`, added
  inside the S4.1 shielded block (errors.rs:148-176) with the same
  additive-serde-tagged pattern. Distinct from `NotSelfVerified` on purpose:
  S4.1 established the 1:1 "one check, one structured reason" convention, and
  a sentinel log that says "not self-verified" for a self-verified token that
  simply didn't opt in to shielded transfers would misroute the operational
  diagnosis. (S4.1's reserved-variant note stands: the additive pattern is
  proven safe — old nodes fail closed on unknown variants.)

### Decision 5 — Step order, the `Validation` error variant, atomic register,
one outbound message

The handler runs the parent's five steps in this order, each fail-closed:

1. `let stx: ShieldedTransaction = deserialize_rmp_to(&message.body)
   .map_err(SentinelError::Encoding)?;`
2. Spec lookup (Decision 3) → build
   `ShieldedValidationDeps { spent: self.pool_view.nullifier_set(),
   roots: self.pool_view.root_history(),
   recency_window: self.env_data.shielded_root_recency }` →
   `spec.validate_shielded(&stx, &self.env_data, &deps)`; any `Err` →
   `SentinelError::Validation(e)` (**before any state is written** — the
   advisory gate precedes registration and sending, exactly the parent's
   "rejects obvious garbage before any finalizer work").
3. `let token = self.data_provider.get_token(&stx.token_id,
   &self.env_data.token_partition_id).map_err(|…| Validation(TokenNotFound))?;`
   → `!token.is_self_verified` → `Validation(NotSelfVerified)` →
   `!token.is_shielded_opt_in()` → `Validation(NotShieldedOptIn)`.
4. `self.registry.register_shielded(&stx)` — atomic
   `DashMap::insert` whose `Some(old)` return means
   `TransactionAlreadyExists` (the `add_transaction` TOCTOU pattern,
   registry.rs:62-74; no `contains` pre-check). Duplicate ⇒ `Err`, and steps
   4→5 ordering means **no outbound message** for a duplicate.
5. `let key = self.assign_finalizer_deterministic(&stx.id,
   *self.current_epoch.lock())?;` (the existing machinery, sentinel.rs:598-630,
   unchanged — same snapshot/domain/salt as standard txs, so the collector
   selection is indistinguishable from a standard tx's) →
   `self.transaction_notifier.send_sign_shielded(&stx, &key, &self.env_data)`.

Supporting additions:

- **`SentinelError::Validation(PneumaticError)`** (new variant, additive;
  `SentinelError` is crate-local and never serialized). No existing variant
  carries a structured `PneumaticError` — `Registry(String)` would flatten the
  S4.1 reason to a string and lose the `ValidationFailureReason` the
  sentinel's log (and S5.2's finalizer, which re-runs the same spec) works in
  terms of.
- **`register_shielded`** on `PendingTransactionRegistry`:
  `shielded_transactions: DashMap<String, ShieldedTransaction>` field +
  `new()` init + `register_shielded(&ShieldedTransaction) ->
  Result<(), PneumaticError>` + `contains_shielded(&str) -> bool` +
  `get_shielded(&str) -> Option<ShieldedTransaction>` (clone-out; the S5.3
  committer's hash match reads through it). Doc comment mirrors `used_nonces`
  (registry.rs:39-43): **append-only, never evicted — there is deliberately no
  remove path in S5.1** (the map's consumer is the committer's H12-style
  comparison, S5.3; post-commit GC is a roadmap item, Risk 3).
- **`send_sign_shielded`** on `TransactionNotifier`: mirrors
  `send_to_finalizer_for_preload` (transaction_notifier.rs:87-106) — body is
  `stx.canonical_bytes()` (the S3.1 binding surface; the finalizer signs
  `stx.hash()` over exactly these bytes in S5.2), action `"SignShielded"`
  (already in `FINALIZER_ACTIONS`, node_server.rs:56-57 — no dispatcher
  change), signed with the sentinel's own identity (never the destination's —
  the `preload_to_finalizer_signed_with_sender_not_destination` discipline),
  `send_to_nodes(NodeRegistryType::Finalizer, payload)` with the existing
  fail-closed `NoTarget`.

The S3.2 stub (sentinel.rs:143-149) is deleted; the match arm at :128 and the
`"ShieldedTransfer"` comment above it stay (the comment's "Real validation +
routing is S5.1" sentence is retired with the stub). No
`TransactionState` variant is added (parent :709-711): the parallel map is
outside the `Pending → … → Committed` machine by construction.

### Decision 6 — Test strategy: stub spec in the default suite, real spec where
it is free, one `#[ignore]`d live prove

The sentinel's default suite must not pay Halo2 keygen. The split:

- **Stub spec (default suite).** A test-only `StubShieldedSpec` in
  sentinel.rs's test module implements `TransactionValidationSpec` with
  `name() == "Shielded"` (the registration name the handler looks up — the
  constant seam is exercised, not mocked away) and a cheap
  `validate_shielded`: `tx.proof.is_empty()` ⇒
  `Err(Validation([InvalidShieldedProof]))`, else
  `Ok(TransactionValidationResult::valid(vec![], <zero risk>))`. It pins
  **wiring** — which spec the handler calls, with which deps (the view's
  nullifier set + root history + the env's K), and what the handler does with
  the verdict (register/send vs short-circuit) — while the real spec's
  *crypto* behavior is already pinned in the core suite (S4.1.5 check-4 tests,
  S4.3.3 concrete-state suite) where the `Lazy` verifier's keygen is already
  paid once per binary.
- **Real spec where it is free (default suite).** The stale-nullifier and
  stale-root sentinel tests register the **real** `ShieldedValidationSpec`
  (via `ValidationSpecRegistry::register_shielded`) against a view whose
  shared state was pre-mutated (a marked nullifier / K+1 pushed roots). These
  reach checks 2/3 and fail there — **before** the check-4 `Lazy` is touched
  (validation.rs:561-570 precedes :582) — so no keygen enters the sentinel
  binary. They prove the handler's deps genuinely reach into the view (a
  fresh-registry bug — "validate against a pristine local copy" — fails
  exactly these two tests).
- **One `#[ignore]`d live end-to-end (S3.3 convention).**
  `handle_shielded_transfer_live_proof_end_to_end` builds a real 1-in/1-out

## 6. Risks & open items

1. **The opt-in key name is a convention, not a protocol constant.**
   `shielded_opt_in` (metadata, value `"true"`) must match what clients write
   at mint. It is centralized in `Token::is_shielded_opt_in` so there is one
   place to change it, but nothing *forces* client and node to agree — the
   failure mode is silent (transfers fail closed with `NotShieldedOptIn`),
   which is the safe direction. **Flag to roadmap owner:** confirm the key
   name with the client/wallet workstream before S5.4's composite end-to-end
   (a mismatch there would surface as "the whole pipeline rejects everything"
   rather than as a wiring bug).
2. **Advisory ≠ consensus — by design, and it cuts both ways.** The sentinel's
   accept is permission to spend finalizer compute; the committer's guarded
   apply (S5.3: step-0 `verify_shielded_proof` re-run, K-recency re-check,
   H12-style hash match against the parallel map) is authoritative, and each
   finalizer re-verifies independently in S5.2. A sentinel with a lagging
   (split-deployment) pool view may *reject* a transfer that would be
   accepted elsewhere (a liveness miss, absorbed by the S4.3 K window and
   client retry) — and it can *accept* one that the committer rejects
   (wasted finalizer compute, zero consensus effect: nothing commits without
   quorum + committer apply). No S5.1 code depends on the sentinel's verdict
   being "correct" — only on it being fail-closed.
3. **Unbounded growth of `shielded_transactions` (inherited design).** The
   map is deliberately never evicted in S5.1 (parent :708-711; the
   `used_nonces` side-map at registry.rs:39-43 has the identical property by
   H14's design). A long-lived sentinel process grows it monotonically with
   shielded traffic. This plan adds nothing for it (the parent item scopes
   eviction out); **note for the parent/roadmap:** a post-commit GC pass
   (prune map entries whose tx id appears in a committed block) is the
   natural fix and belongs with S5.3/S6, where commit events are visible.
4. **The composite's shielded path is inert until S5.4 — correctly so.**
   Until S5.4 swaps the placeholder for the real `Arc<ShieldedPool>`, a
   composite sentinel validates against a pristine genesis-seeded view: every
   non-genesis transfer is rejected fail-closed (`StaleMerkleRoot`) and no
   `SignShielded` is sent. That is the *Decision 2* property doing its job,
   not a gap — but it means S5.1's "reaches the finalizer" verify is proven
   in the sentinel unit tests (with a view whose state the test controls)
   and the `#[ignore]`d live test, and the composite-level proof lands in
   S5.4 with the real pool. Anyone demoing shielded transfers before S5.4
   will see the fail-closed rejections.
5. **One K, one source of truth.** The sentinel reads
   `env_data.shielded_root_recency` at call time (S4.3's consensus parameter);
   the placeholder view is constructed with the *same* env value in
   `build_runtime`. There is no second K to drift in the composite. S4.3's
   Risk 1 applies unchanged at deployment scope: a node running a different
   K than its peers is a split brain — enforced by deployment process, not
   code.
6. **`SignShielded` currently lands on a stub.** S5.1's outbound message
   reaches the finalizer's S3.2 fail-closed dispatch stub until S5.2 swaps in
   `handle_sign_shielded` — so a fully valid S5.1 transfer ends with "no
   votes, no commit" and the tx sitting in the sentinel's parallel map. This
   is the intended phase boundary (sentinel-side verify scope: "reaches
   Finalizer"), and S5.2's plan must account for the in-flight txs its
   handler makes resumable.
