# Phase S4.2 Implementation Plan — `NullifierRegistry`

> Expanded, actionable implementation plan for **Phase S4.2** of
> [`pneumatic-shielded-implementation-plan.md`](pneumatic-shielded-implementation-plan.md)
> (the "Nullifier-set registry" item in Phase S4).
>
> Scope: the *consensus-critical spent-nullifier set* and its atomic API,
> in `pneumatic_core::registry`. S4.2 builds the data structure the double-spend
> defense reads and writes: S4.1's check 2 *reads* it (via the
> `NullifierMembership` interface S4.1 defined), S5.1 (sentinel) and S5.3
> (committer) *write* to it. What S4.2 deliberately does **not** do —
> persistence, the single-writer guard, rollback unwind — is S5.3's
> `ShieldedPool` job; the scope boundary is stated in *Decision 4*.

---

## 1. Context & what S4.2 delivers

Roadmap 2.5 locks the nullifier set as **consensus-critical, append-only,
durable, globally-agreed** — "first-class in `committer`, not a bolt-on
`HashSet`". The parent plan's S4.2 item specifies the core-crate half of that:

- `NullifierRegistry` in `src/registry.rs`, a new struct **alongside**
  `PendingTransactionRegistry` (which stays untouched).
- DashMap-based, mirroring the file's conventions: mutating methods return
  `Result`, and the check-or-insert uses DashMap's atomic
  **`insert`-returns-old-value** — "the same fix `add_transaction`
  (registry.rs:62-73) and `used_nonces` (registry.rs:192-206) got" — so there
  is **no TOCTOU window** between "is it spent?" and "mark it spent".
- API: `try_mark_spent(nullifier) -> Result<(), PneumaticError>` (Err
  `StaleNullifier` if present), `contains(nullifier)`, `mark_many_atomic(
  &[[u8;32]])` (all-or-nothing: check all, then insert all — a tx with 2
  nullifiers must not spend one and reject on the other).
- **Nullifiers are never removed** — the "never evicted" invariant
  (`used_nonces`-style comment, registry.rs:38-42), enforced by the type
  exposing **no removal API at all**.
- Growth: v1 is unbounded (documented; 32 B/spend — 10M spends ≈ 320 MB;
  compaction is a future item, **not built now**).

### Deliverables

- `NullifierRegistry` + the four methods + `len`/`is_empty` observability
  (`src/registry.rs`), with the consensus-critical / never-evicted / growth
  doc comments.
- `impl NullifierMembership for NullifierRegistry` — closes S4.1's
  interface seam (the S4.1 plan's Open item 6: "S4.2 must re-run those same
  discriminators against the concrete implementation").
- Re-export in `src/lib.rs` alongside `PendingTransactionRegistry`
  (lib.rs:19).
- The S4.1 check-2 discriminator re-run **against the concrete registry**
  (build item S4.2.4), plus the parent item's concurrency discriminators.

### Ground rules applied

- **Additive only.** One new struct in one file + one re-export line. No
  `Transaction`, no `SignedTransaction`, no `ShieldedTransaction` field, no
  action string, no wire change of any kind (see *Wire-compat note*).
- **Fail closed.** A double-mark is `Err(Validation([StaleNullifier]))` —
  the exact structured reason S4.1's check 2 surfaces — never a silent
  overwrite, never a panic.
- **Existing behavior untouched.** `PendingTransactionRegistry`,
  `TransactionSignatureRegistry`, and every existing test pass byte-identical.
  (The `shielded_transactions` parallel map on `PendingTransactionRegistry`
  named in the parent plan is **S5.1's** addition, not this phase's.)

## 3. Design decisions (the meat of S4.2)

### Decision 1 — Error shape: `Validation([StaleNullifier])`, not `Registry(String)`

`PendingTransactionRegistry`'s duplicate rejections use the generic
`PneumaticError::Registry(format!(…))` (registry.rs:68). `NullifierRegistry`
deliberately does **not** copy that. Every failed mark returns:

```rust
Err(PneumaticError::Validation(vec![ValidationFailureReason::StaleNullifier]))
```

Why:

1. **1:1 with S4.1 check 2.** The sentinel's advisory spec (S5.1) and the
   committer's authoritative check (S5.3) already surface *exactly this*
   reason for a spent nullifier (validation.rs:563; S5.3's step 2). The
   registry returns the same structured reason, so no translation layer
   exists anywhere on the path — the reason a client/sentinel sees is the
   reason the consensus structure produced.
2. **S6.2 asserts exact named errors** ("all six rejected with the exact
   named errors"). A `Registry(String)` payload would force S6.2 to string-
   match; `Validation([StaleNullifier])` matches the established
   `reason_matches` idiom.
3. **`Shielded(String)` stays distinct** (S4.1's contract): `Shielded` is
   for pool/tree/registry-*infrastructure* failures (corrupt persisted
   state in S5.3, tree errors); a *semantic* double-spend is `StaleNullifier`.

### Decision 2 — All-or-nothing on a DashMap that has no multi-key transaction

DashMap gives no batched/atomic multi-key operation. `mark_many_atomic` is
therefore **two-phase with conditional rollback**:

```rust
pub fn mark_many_atomic(&self, nullifiers: &[[u8; 32]]) -> Result<(), PneumaticError> {
    // Phase 1 — check ALL before touching state (fail fast, no partial write).
    for n in nullifiers {
        if self.nullifiers.contains_key(n) {
            return Err(PneumaticError::Validation(
                vec![ValidationFailureReason::StaleNullifier]));
        }
    }
    // Phase 2 — insert ALL, recording what THIS call inserted.
    let mut inserted = Vec::with_capacity(nullifiers.len());
    for n in nullifiers {
        match self.nullifiers.insert(n, ()) {
            None => inserted.push(*n),
            Some(()) => {
                // A concurrent spender landed between phase 1 and now.
                // Roll back exactly this call's own phase-2 inserts.
                for k in &inserted {
                    self.nullifiers.remove(k);
                }
                return Err(PneumaticError::Validation(
                    vec![ValidationFailureReason::StaleNullifier]));
            }
        }
    }
    Ok(())
}
```

**Why this is all-or-nothing (the soundness argument — load it, then state
it in the code comment):** the type has **no removal API** (Decision 3).
Therefore:

- A key whose phase-2 `insert` returned `None` was *absent immediately
  before that instant* — and the only code that can ever remove a key is a
  failed batch rolling back **its own** phase-2 inserts.
- When this call detects a collision and removes `inserted`, every key it
  removes is one it itself inserted in this call, a moment ago, having
  verified it was absent. The post-rollback state is bit-identical to the
  pre-call state, plus the concurrent spender's legitimate mark.

So a batch is observably **fully applied, or fully absent** — which is the
parent item's "check all, then insert all" with the race case closed. The
single-key `try_mark_spent` needs no phase 1 at all: its one `insert`
returns the old value, which *is* the atomic check-or-insert (the
`used_nonces` idiom verbatim) — zero TOCTOU.

**Known edge (documented, tested):** a batch containing the *same*
nullifier twice collides with its own first insert in phase 2 → the batch is
rejected and rolled back. This is the fail-closed reading ("a nullifier
cannot be spent twice, not even by one tx"); on the wire path S4.1 check 1
(pairwise-distinct, `InvalidCommitment`) rejects the shape first, so the
registry behavior is defense-in-depth, never a new rejection surface.

### Decision 3 — "Never evicted" is enforced by the type, not by discipline

The parent item says nullifiers are never removed — "a rollback that
un-spends a nullifier is a double-spend" (roadmap 2.5: the set is
**append-only**). S4.2 makes this a structural fact:

- `NullifierRegistry` exposes **no remove/unmark/mark-removed method of any
  kind**. The only `remove` calls in the type are the internal phase-2
  rollback of Decision 2 (which restores the pre-call state of a *failed*
  call — it never un-spends a nullifier that any successful call marked).
- The struct field is private; the test module is the only other place that
  touches it, and only to *read* state in assertions.
- A doc comment on the type records the invariant and names the reason
  (roadmap 2.5), mirroring the `used_nonces` comment style
  (registry.rs:38-42).

> **Consequence to flag (Open item 1):** the parent plan's S5.3
> conflict/rollback bullet says rollback "remove[s] exactly this block's
> nullifiers". Taken literally that *un-spends* a nullifier — the exact
> double-spend roadmap 2.5 forbids, since the nullifier set is global and
> shared across per-token chain branches (two divergent blocks can spend the
> same note; a set that shrinks on reorg lets both stand). S4.2's half of
> the reconciliation is fixed: no delete API exists for S5.3 to call.
> **Recommendation to the roadmap owner:** S5.3's rollback pops the loser
> block's *tree leaves* and drops its *applied-update delta*, but leaves the
> nullifiers **marked** (Zcash semantics: reorgs never un-spend). If the
> owner instead intends tip-only un-marking, S5.3 must add a guarded
> `unmark` seam — and that decision belongs to S5.3's plan, with roadmap 2.5
> cited against it. S4.2 builds nothing for that case.

### Decision 4 — Scope boundary with S5.3's `ShieldedPool`

S4.2 is the **in-memory consensus structure**. The parent plan assigns to
S5.3: the single-writer guard (cross-token ordering — "one lock, no
concurrent root advances"), durability via the data provider (nullifiers
persisted *before* commit is reported), load-at-boot fail-closed, and
rollback unwind. Therefore S4.2:

- **Does not** take external locks, does not persist, does not load at
  boot. (The committer's pool wraps `Arc<NullifierRegistry>` — S5.3 threads
  it in `build_runtime`/`BlockServices`; the registry is `Send + Sync`
  because `DashMap` is, so the `Arc` sharing is free.)
- **Does not** define `ShieldedPool`, the applied-update map, or any
  committer code.
- **Does** keep the API shape S5.3 needs: `mark_many_atomic` is the
  S5.3 step-4 "all-or-nothing" primitive ("`mark_many_atomic` (S4.2,
  all-or-nothing) + append commitments … atomically with the chain append,
  under the same guard" — S5.3 composes it under *its* guard; S4.2's
  atomicity is the within-set guarantee, S5.3's guard is the cross-structure
  ordering guarantee).
- **Does** document on the type that persistence is the pool's job, so a
  future reader of `registry.rs` doesn't assume the set survives restart.

### Decision 5 — Exact API surface & convention mapping

| Method | Signature | Convention source |
|---|---|---|
| `new` | `-> Self` (`#[derive(Default)]` + explicit `new`, as both existing registries) | `registry.rs:29, 46, 311, 318` |
| `try_mark_spent` | `(nullifier: [u8; 32]) -> Result<(), PneumaticError>` | mutation → `Result` (file rule, registry.rs:13-14) |
| `mark_many_atomic` | `(&[[u8; 32]]) -> Result<(), PneumaticError>` | mutation → `Result` |
| `contains` | `([u8; 32]) -> bool` | pure read → plain value, exactly as `PendingTransactionRegistry::contains` (:57) and `TransactionSignatureRegistry`'s read side |
| `len` / `is_empty` | `-> usize` / `-> bool` | `TransactionSignatureRegistry::len`/`is_empty` (:385-392); needed by S5.3 observability and the concurrency-test assertions |

Nullifier key type is `[u8; 32]` (the exact output of `nullifier()`,
note.rs:143) — `Eq + Hash + Send + Sync`, DashMap-eligible, and the same
type the wire carries in `ShieldedTransaction.nullifiers`
(transactions.rs:371) and in `NullifierMembership::contains_nullifier`
(validation.rs:408) — no conversion anywhere.

## 5. Wire-compat note (ground rule 4)

**No wire change of any kind.** `NullifierRegistry` is node-local consensus
state:

- No new action string, no new payload schema, no new message.
- No field added to `Transaction`, `SignedTransaction`, or
  `ShieldedTransaction` (the nullifiers already ride the wire inside
  `ShieldedTransaction.nullifiers`, defined by S3.1 — this phase only
  decides, per-node, whether they are *accepted*).
- The set is not gossiped: it is replicated **by replay** — every node
  rebuilds it from committed block history (S3.1: the pool update is
  hash-bound inside `signed_trans.shielded`), and the S4.3 K-recency window
  absorbs view lag in split deployments (S5.1's pool-view design).
- Old nodes see no difference (they already fail closed on
  `"ShieldedTransfer"` per S3.2). New→old / old→new decode paths are
  untouched.
- The only observable wire-adjacent behavior is *rejection semantics*: a
  double-spent nullifier is now rejectable with the exact
  `StaleNullifier` reason — which S4.1 already introduced as an additive
  serde-tagged enum variant (its own wire note stands; this phase adds no
  variant).

## 6. Risks & open items

1. **HEADLINE — S5.3 rollback vs roadmap 2.5 (Decision 3).** The parent
   plan's S5.3 bullet ("remove exactly this block's nullifiers" on
   tip-rollback) would un-spend nullifiers, contradicting roadmap 2.5's
   append-only, globally-agreed set and reopening the double-spend across
   divergent per-token branches. S4.2 hardens its own half (no delete API
   for S5.3 to call) and **flags the rest to the roadmap owner**:
   recommended resolution is S5.3 rollback pops leaves + drops the
   applied-update delta, **leaving nullifiers marked** (Zcash reorg
   semantics). If the owner rules for guarded un-marking, S5.3's plan must
   define that seam explicitly — with 2.5 cited against it — and S4.2
   would gain a deliberately dangerous, guard-only method. Decide before
   S5.3 starts; S4.2 is neutral on the call and builds nothing for it.
2. **Two-phase batch soundness rests on the no-delete invariant.**
   `mark_many_atomic` is atomic *because* nothing can remove keys (Decision
   2's argument). The invariant is enforced structurally (no public
   removal API) and documented at both the type and the method. If any
   future item adds a removal path (see item 1), this argument must be
   re-audited in that item's plan — flagged here so it isn't forgotten.
3. **Unbounded growth (v1 by design).** 32 B/spend, 10M spends ≈ 320 MB,
   no eviction, no compaction — documented on the type as a future item
   (Orchard-style compaction is research, out of Tier 1). S6 should record
   a size probe so the number is measured, not assumed.
4. **`len`/`is_empty` are observational, not consensus inputs.** They read
   DashMap's shard-counted length; S5.3 must not derive a *consensus*
   decision from them (it should re-check `contains`/`mark_many_atomic`,
   which are the authoritative operations). Documented to prevent a
   future "optimization" through the cheap read.
5. **No live-prove in this phase** — the one S4.2 test that reaches check 4
   (S4.2.4 contrast) reuses S4.1's `Lazy<ShieldedVerifier>`; if S4.1's
   keygen cost ever moves the core-lib binary's run time, it moves with
   S4.1's tests, not this phase's.
